Propósito

¿Por qué evolucionar de v1 a v2?

v1.0.0 (PMOA) demostró que el ranking semántico, la extracción de entidades, la auditoría y la gobernanza de memoria son viables. Pero quedó acotado a un solo dominio: IT Operations.

Usuario objetivo

Usuario Universal con IA — 5 roles, dominio-agnósticos

v2.0.0 se diseña para cualquier profesional que necesite memoria aumentada. Los roles se gestionan vía Keycloak RBAC.

RolNecesidad principal
Memory OperatorCrear, clasificar y relacionar memorias en cualquier dominio
Memory ReviewerAprobar o rechazar memorias que requieren revisión humana
Memory ConsumerConsultar memoria relevante, confiable y actualizada
Memory AdministratorDepurar, archivar, fusionar y gestionar tenants
Memory AuditorVerificar trazabilidad, cumplimiento y cobertura de conocimiento

3 perfiles de dominio (configuraciones que adaptan el core sin modificar la API): Ops Profile (SRE, DevOps), Agent Profile (agentes IA, chatbots), Business Profile (CRM, Legal, Finanzas).

Visión del producto

Motor de memoria aumentada para cualquier profesional

Principios del core genérico

  • 8 kinds universales: fact, preference, event, decision, task, procedure, note, entity
  • 6 estados de ciclo de vida: draft → pending → active | rejected → archived → deleted
  • 9 tipos de relación: related_to, depends_on, caused_by, resolves, contradicts, supports, mentions, belongs_to, supersedes
  • 4 niveles de sensibilidad: public, internal, confidential, secret
  • Scoping multi-tenant: tenantId + userId + sessionId + namespace
  • English-Only internals: interoperable con ecosistemas internacionales de IA

Decisiones técnicas clave

API v1 descartada · Stack flexible con ADR

API v1

Decisión del sponsor (2026-05-03): v1.0.0 está cerrado. Nadie usa v1 en producción.

  • No coexiste con v2
  • No hay período de transición
  • Solo /api/v2/
  • Sin dependencia de código ni esquemas heredados
  • Migración v1→v2 es script externo opcional

Beneficio: libertad total de stack.

Stack

Restricción R-01: se permite cambiar componentes si se justifica mediante ADR.

  • Backend: Quarkus o alternativa (ADR)
  • Base vectorial: Qdrant o alternativa (ADR)
  • Embeddings: OpenAI o alternativa (ADR)
  • BD relacional: PostgreSQL
  • Auth: Keycloak (OIDC)
  • Infra: Docker + Caddy + HTTPS

Decisión final en Fase 3 (Diseño Técnico).
