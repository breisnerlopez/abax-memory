Contexto funcional

Problema y objetivo del producto

PMOA busca capturar, validar, reutilizar y auditar conocimiento operativo para reducir pérdida de conocimiento, tiempos de búsqueda e inconsistencia entre agentes.

  • Problema actual: conocimiento disperso, manual y poco trazable.
  • Objetivo MVP: repositorio único de memorias operativas reutilizables.
  • Modelo operativo inicial: backend + API REST + flujos Git/GitHub.
Roles cubiertos

Operador de memoria, revisor/validador, consumidor operativo, administrador de memoria y auditor/owner de dominio.

Observación de alcance

Al no existir aún especificación funcional, reglas, diagramas y criterios formales de Fase 2, la presente propuesta debe usarse como insumo de validación y no como baseline definitivo.

Alcance MVP

Qué sí incluye

  • Alta manual y alta desde caso.
  • Memorias en Markdown con frontmatter obligatorio.
  • Validación estructural y validación humana por criticidad.
  • Búsqueda semántica con filtros estructurados.
  • Trazabilidad, versionado Git, estados y archivado.
Fuera de alcance MVP
  • UI dedicada para usuarios finales.
  • Orquestación general de agentes.
  • Visibilidad granular por memoria.
  • Multi-repositorio y portabilidad avanzada.
  • Aprobación automática de memorias críticas.

Proceso clave

Flujo funcional extremo a extremo

1. Captura

Crear memoria manual o desde caso con metadata mínima.

2. Clasificación

Asignar tipo, dominio, origen, criticidad y relaciones.

3. Validación

Validación estructural automática y PR humana para criticidad alta/crítica.

4. Publicación

Persistir en Git, registrar trazabilidad e indexar para búsqueda.

5. Reutilización

Consultar por API, buscar semánticamente y depurar con archivado.

Resultado esperado: memoria confiable y reutilizable Punto de control: criticidad define el nivel de revisión

Reglas principales

Reglas de negocio propuestas para el MVP

ID Condición Acción Excepción
RB-01 Falta metadata obligatoria en frontmatter. Rechazar creación/publicación e informar campos faltantes. Ninguna.
RB-02 La memoria altera datos, configuración o cumplimiento. Clasificar al menos como alta. Solo redefinición formal del negocio.
RB-03 Memoria alta o crítica. Exigir revisión humana por PR antes de aprobar. Ninguna en MVP.
RB-04 Memoria archivada o duplicada. Excluir de consultas activas por defecto. Consulta explícita por estado.
RB-05 Se elimina una memoria bajo control. Retirar del sistema activo con evidencia auditable. Capacidad diferida a release posterior.
